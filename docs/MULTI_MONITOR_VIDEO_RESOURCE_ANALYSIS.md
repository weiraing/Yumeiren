# 多屏视频资源分析（阶段 5 交付物）

## 1. 当前多屏架构（代码事实）

`VideoWallpaper`（`src/videowallpaper.cpp: layoutOutputs()`）三种模式：

| 模式 | 输出结构 |
|---|---|
| PrimaryScreen（主屏显示，默认） | 1 套输出：QVideoWidget+QMediaPlayer+QAudioOutput |
| StretchAll（全屏拉伸） | 1 套输出，几何=所有屏幕联合矩形 |
| MirrorAll（多屏镜像） | **每屏 1 套输出**（首屏承载音频轨，其余 muted；同一 URL 各自 setSource） |

即镜像模式下屏幕 N 的资源形态：

```text
屏幕 i → QMediaPlayer i（独立打开同一文件、独立解码、独立帧池/表面） → QVideoWidget i
```

- 播放器创建仅发生在 `m_outputs` 为空时（`ensureOutputs` 非空只轻量重挂载）；模式值不变不重建（`setScreenMode` 幂等）。
- 切换视频对 N 套输出统一 `setSource`/`setPosition`；错误推进仅由首个输出驱动。

## 3. 任务书 8.4 十问回答

1. **多屏是否创建多个播放器？** 是——仅 MirrorAll 模式每屏一套（主屏/拉伸模式单套）。
2. **是否共享同一媒体源？** 否：每套播放器各自 `setSource` 同一 URL，后端各自完整解码（无共享 demuxer/解码器的公开机制）。
3. **每屏是否独立视频输出？** 是（独立 QVideoWidget + 独立 WorkerW 挂载）。
4/5. **内存/显存是否线性增加？** 推断近似线性（见上），待双屏实测。
6. **是否存在播放器重复创建？** 无（幂等守卫齐备，两阶段实验零累积实证）。
7. **能否不换底层架构减少资源？** 公开 API 内无"单播放器多 QVideoWidget"；唯一路由方案是 QVideoSink 自绘，已被本机 A/B 实验否定（内存 +20~28%、CPU ×5.5，且多屏还需 N 份 CPU 帧转换，比现状更糟）。
8. **是否值得做"单播放器多输出"实验？** 不建议：Qt 公开 API 不支持直接绑定多输出；若经 sink 中转则同时承担方案 C 与 sink 路径的双重成本。仅当用户实际多屏场景明确且可接受 CPU 上升时才重新评估。
9. **API 限制？** 是：`QMediaPlayer::setVideoOutput` 单输出绑定；QVideoFrame 无跨输出共享呈现的公开机制。
10. **稳定性风险？** 高：多 sink 同步、异尺寸缩放、生命周期与挂载管理复杂度显著上升，与"稳定性优先"的本阶段目标相悖。

## 4. 方案对比与建议

| 方案 | 适用前提 | 结论 |
|---|---|---|
| A 保持现状（每屏一套） | 多屏使用比例低、稳定性优先；资源增量 = 线性可预期 | **✅ 建议（当前决策）**：已有幂等/释放/挂起机制全覆盖；任务书 8.5 要求"实验确认开销明显且用户确实需要"才升级 |
| B 共享媒体源+独立输出 | Qt 无公开 API 支持共享 demuxer | ✗ 不可行（不引入私有 API/自研 demuxer） |
| C 单播放器多输出实验 | 仅独立分支、必须先过 API 可行性 | ✗ 被 sink A/B 数据 + API 限制双重否定 |

**后续触发条件**：接入双屏硬件补测 M2/M3/M5/M6（脚本就绪）；若实测确认资源线性增长且用户反馈多屏为高频场景，再评估是否重启方案 C（预期仍为否定）。
