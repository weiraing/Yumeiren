# 资源占用优化措施与实测数据（持续更新）

视频壁纸的资源占用主体是 Qt FFmpeg 后端的解码管线（归因见 `perf/memory-attribution.md`：固定 ~210MB + ~88MB/百万像素，GPU 显存近似同比例）。应用层在**不牺牲画质、不关闭硬解、不替换架构**的前提下，已落地的降低手段如下（均经实测）：

## 1. 资源友好模式（默认开启，2026-09-14 新增）

- 机制：启动时把进程亲和性限制到前 **4 个逻辑核**——Qt FFmpeg 后端的解码线程数跟随 `QThread::idealThreadCount`（受亲和性掩码影响），线程池与解码缓冲随之收缩。
- UI：视频壁纸页"资源友好模式"复选框（默认勾选；`video/affinityLimit`，**重启生效**）。
- 实现：`desktopmount.cpp applyProcessAffinityLimit()`，`main.cpp` 在 QApplication 构造后立即调用（使全部后续线程继承掩码）；核数 ≤4 的机器自动跳过。

实测（32 逻辑核机，1080p30，稳态 80s）：

| 配置 | Private | GPU 专用显存 | 线程 | CPU | GPU 利用率 |
|---|---:|---:|---:|---:|---:|
| 全核 32 | 408MB | 234MB | 105 | 0.20% | 25.4% |
| 限 8 核 | 331MB（-19%） | 180MB | 98 | 0.19% | 23.8% |
| **限 4 核（默认）** | **296MB（-27%）** | **149MB（-36%）** | 93 | **0.20%** | 23.6% |

4K60 压力确认（限 4 核 80s 连续播放）：Private 642MB（全核 928MB，**-31%**）、CPU 0.31%、无中断无退化。硬解仍在 GPU（d3d11va），CPU 收敛是 demux/送帧线程减少所致。

## 2. 已有的其他占用控制（按生效场景）

| 措施 | 效果 | 触发 |
|---|---|---|
| 帧率上限（默认 24FPS） | 4K60 实测 CPU -62%、GPU 占用率 -50%、内存 -8% | 高于 24fps 的素材按比例慢放 |
| 音量 0 禁用音频轨 | 音频解码线程/设备归零 | 音量为 0（默认） |
| 空闲工作集回收 | WS 释放（Private 不变，非真实释放） | 故意空闲 30s |
| 挂起自动卸载管线 | Private -70%+、GPU → 0 | 全屏/遮挡/锁屏/熄屏持续 180s |
| 错误曲目失败名单 | 防坏素材乒乓循环造成的解码器重建churn | 曲目跳过即入名单 |
| 素材策略（AV1/HEVC/1080p） | AV1 -34%、HEVC -9%、1080p 素材为 4K 的 ~43% | 见 VIDEO_MEDIA_COMPATIBILITY_POLICY.md |

## 3. 已排除的方向（有数据支撑，勿重复尝试）

- `QVideoSink` 自绘管线：内存 +20~28%、CPU ×5.5（第二阶段 A/B 实测）。
- `QT_MEDIA_BACKEND=windows`（WMF）/GStreamer：违反任务书"不引入 MF 等后端"约束。
- 解码线程环境变量旋钮：扫描 Qt6Multimedia.dll 仅 4 个 `QT_*` 开关，无线程数配置——亲和性是等效且合法的途径（即措施 1）。
- 关闭硬解 / 降分辨率播放：违反约束（画质红线）。

## 4. 剩余边界

- 4K60 高码率素材长循环存在台阶式显存扩张（~2GB 平台，驱动/后端解码池扩容，非应用层泄漏）。
- 多屏镜像 = 每屏一套解码管线（线性增长），方案评估见 MULTI_MONITOR_VIDEO_RESOURCE_ANALYSIS.md。
- 1080p30 的 ~300MB（资源友好模式后）为后端固有成本，进一步压缩需自研管线。
