## 3. 测试步骤

所有用例走同一套流程（`tools/perf/run_case.ps1`），目的是让被测路径与用户真实路径一致：只改 `config/.ini`，不改应用代码、不改缓存目录、不改命令行参数。

1. 备份 `new-build/config/.ini` 到 `%TEMP%\yumeiren_perf_cfg_<tag>.ini`；
2. 重写 `[video]` 段播种场景（`wasPlaying=true` 让应用走自动起播路径，播放列表用正斜杠写入以绕开 QSettings 的转义）；
3. 清理同名残留实例（测量必须独占，进程内有单实例互斥锁）；
4. 需要场景开关时设置环境变量：`YUMEIREN_AUTO_STOP_MS` / `YUMEIREN_AUTO_START_MS` / `YUMEIREN_AUTO_PAUSE_MS` / `YUMEIREN_DIAG`；后端与硬解对照用 `QT_MEDIA_BACKEND`、`QT_FFMPEG_DECODING_HW_DEVICE_TYPES`；
5. `Start-Process` 启动 `YumeirenTest.exe`（工作目录 = `new-build`），等 5 s 预热；
6. `probe.ps1` 周期采样工作集、私有提交、CPU、线程、句柄、全部 GPU 引擎与 `GPU Process Memory` 计数器，写 `new-build/perf-results/<tag>.csv`；
7. `CloseMainWindow()` 正常关窗（走 `VideoWallpaper::shutdown()` 收口），10 s 超时才强杀；
8. 复制 `.cache/logs/videowallpaper.log` 到 `perf-results/<tag>.log`，**还原用户配置**，删除本用例设置的额外环境变量。

矩阵与汇总命令：

```powershell
# 阶梯素材生成（只需一次）
pwsh -NoProfile -File tools/perf/make_fps_ladder.ps1
# 改动前基线 / 改动后与开关对照
pwsh -NoProfile -File tools/perf/run_matrix.ps1 -Matrix baseline
pwsh -NoProfile -File tools/perf/run_matrix.ps1 -Matrix verify
# 短时回归 + 长稳
pwsh -NoProfile -File tools/perf/run_regression.ps1 -Group short
pwsh -NoProfile -File tools/perf/run_regression.ps1 -Group soak
# 汇总（必须用 -Pattern，多标签逗号列表会被 agg 丢弃）
pwsh -NoProfile -File tools/perf/agg.ps1 -Pattern 'b_*'  -OutCsv new-build/perf-results/summary_baseline.csv
pwsh -NoProfile -File tools/perf/agg.ps1 -Pattern 'v_*'  -OutCsv new-build/perf-results/summary_verify.csv
pwsh -NoProfile -File tools/perf/agg.ps1 -Pattern 'r_*'  -OutCsv new-build/perf-results/summary_regression.csv
```

分段统计（长稳要看 10 min / 20 min / 30 min 三个时间点，`agg.ps1` 只给全段均值且丢 0 值，因此按 `elapsed_s` 窗口单独算）：

```powershell
pwsh -NoProfile -File tools/perf/win_stats.ps1 -Csv new-build/perf-results/r_soak30_1080p30.csv -Lo 0 -Hi 2500 -Step 600
```

观测结论：

1. **内存跟分辨率走，不跟帧率走**。1080p 五档（15/24/30/60/60dup/still）全部落在 302–353 MB，4K 三档落在 673–782 MB，约 2.2 倍，与 1080p→4K 的 4 倍像素不成比例，说明大头不是单帧缓冲。
2. **编码格式改变内存水位**：同为 4K60，H.264 阶梯素材 673 MB、101 Mbps 原片 746 MB、AV1 782 MB。AV1 比同尺寸 H.264 多 109 MB（+16 %）。
3. `b_1080p24` 的 +107.5 MB drift 是这批里唯一显著的单向漂移，但**归因已改判**（⚠ 两处数字同源）：不是循环边界叠加，而是 §9 的**桌面窗口重绑**污染。Private 逐点轨迹 324.6 / 325.0 / 270.2 / 270.3 / 321.2 / 354.9 / 315.1 → **378.3 / 421.2 / 421.5 / 425.4**，在 elapsed 60.9→68.8 之间一次跳完（与该会话 12:00:03.484 的重绑时刻对齐），此后停在高位不再回落；Dedicated 同步由 149.1 跳到 241.5，所以 190.2 也是混合均值而非稳态。对照：`b_1080p30`（同素材家族、约 9 次循环、会话内无重绑）drift 只有 +4.1 → 普通循环不产生这种台阶跃。详见 §9.1。
4. 长稳（§9）显示真正的一次性抬升发生在**桌面窗口重绑**时，与帧率 / 码率无关。

观测结论（每条都能在本表内自证）：

1. **3D 成本按呈现帧数结算，与画面内容无关**。1080p 阶梯 15 / 30 / 60 fps 的 3D 占用 7.1 / 15.4 / 31.2 %，折算单帧 0.47 / 0.51 / 0.52 %，斜率线性；`b_60dup`（30 fps 内容复制成 60 fps）= 31.6 %，与真 60 fps 的 31.2 % 一致；`b_still30`（静帧）= 13.7 %，与 `b_1080p30` 的 15.4 % 同档。因此「让画面静止」不省钱，少送帧才省钱。同时 1080p60 的 3D 只有 31.2 %，说明本机呈现回路并未运行在 165 Hz 全速率，否则单帧成本会被摊薄。
2. **单帧成本 ∝ 源像素数**。`b_1080p60` 0.52 %/帧 vs `b_2160p60` 87.6 / 60 = 1.46 %/帧，比值约 2.8；更能说明问题的是同帧率对照：`b_1080p30` 0.51 vs `b_2160p30` 1.92 %/帧，比值 3.76，接近像素比 4.0。结论：Qt 的 FFmpeg 插件在本机没有做上传前缩放，4K 素材即使窗口只有 2560×1600，也是按 3840×2160 上传。
3. **4K60 的 3D 已饱和**。三条不同的 4K60 素材（H.264 阶梯 87.6、AV1 88.2、101 Mbps 原片 88.3 %）都停在 87–88 % 且互不分离，而 4K30 只有 57.5 %；按单帧成本 1.92 % 外推 60 fps 需要约 116 %。这是「上限被压平」的形态，据此推断 4K60 存在掉帧，属**推断**而非帧级证据（见 §10）。
4. **显存池 ∝ 源像素，与帧率无关；编码格式改变池大小**。Dedicated：1080p 各档 149.0–149.1；4K30 与 4K60 同为 434.0 / 433.8 → 帧率不加显存；AV1 910.0、101 Mbps 原片 555.2、H.264 阶梯 433.8 → 同分辨率下 AV1 需要 2.1 倍解码缓冲。
   **勘误（复核后改判）**：本条原文把 `b_1080p24` 的 190.2 当成「1080p 唯一例外」，并声称在切素材用例里精确复现。两条都不成立。逐点 CSV 显示该用例 Dedicated 是 **149.1（elapsed 21.4–60.9 共 5 点）→ 241.5（elapsed 68.8–92.5 共 4 点）的一次阶跃**，聚合器丢掉前 2 点后取整段均值 = 190.17，即一个任何时刻都不存在的数；阶跃时刻与该会话日志 12:00:03.484 的壁纸窗口重绑事件（elapsed ≈ 66 s）严格对齐。切素材用例 `r_switch`（会话 12:46:08.901，内部**无**重绑）29 个样本的 Dedicated 全在 136.5–149.6，均值 140.8，从未出现 190.2 → **1080p 各档（含 24fps）稳态池就是 149.x，无特例**。真正的额外规律是「重绑会换一套更贵的池」，见 §9。
5. **限核不改变 GPU 占用，但改变显存**。1080p30：GPU 总 25.7 → 27.6，3D 15.7 → 17.5（同档波动）；Dedicated 237.4 → 149.1（−37 %）。4K60：3D 77.4 → 76.7（不变），Dedicated 693.0 → 406.0（−41 %）。说明「资源友好模式」的实际收益是**解码器/驱动按核数分配的缓冲池变小**，不是限制 GPU。
6. **WMF 后端多一条 Copy 通道**（仅 1080p 一项成立）。`v_wmf_1080p30`（会话内无重绑）除 3D 17.3 % 外另有 Copy 引擎 3.23–3.32 %，11 个样本平稳，同会话句柄恒为 4 018–4 026、线程 88–92 → WMF 的句柄 +36 % 是真实的后端差异。4K60 一项**作废**：该会话 elapsed 40 s 处发生重绑，Copy 11.2–11.5 % 只存在于重绑前的 4 个样本，之后直接归 0（不是「稳态 11.3 %」），而线程 92→123、句柄 4 030→4 580 同样是重绑造成的，不能记在 WMF 头上。结论「保持 FFmpeg 默认」仍由 1080p 的干净对照（Private −13.6 %、句柄 −36 %）支撑。
7. **关掉硬解后 `VideoDecode` 计数器消失**（`v_swdecode_1080p30`），全部占用挪进 3D 引擎（12.5 %），CPU 从 0.3 涨到 0.9，私有内存反而降到 217.5 MB。这既证实默认路径确实走硬解，也说明「省显存」的代价是 CPU 与解码帧率上限，不能当成优化手段。
8. **暂停是真的零 GPU**。`v_pause_cycle` 暂停段 GPU 总占用 0–0.06 %、3D ≈ 0、VideoDecode 无样本，工作集从 130 MB 掉到 2.9–26.5 MB，而 Dedicated 仍是 149.1 MB 不变 → 暂停只释放 CPU/GPU 时间，不释放已分配的显存池。

观测结论：

1. **CPU 只跟帧率有关，跟分辨率基本无关**。1080p 阶梯 0.1 → 0.5（15 → 60 fps），而 4K60 只有 0.4，比 1080p60 的 0.5 略低；4K30 0.3 = 1080p30 的 0.2 同档。原因见 §6.7：默认走硬解，像素量落在 GPU 的 VideoDecode / 3D 引擎上，CPU 只做解封装与提交。
2. **硬解是真的在生效**。强制软解后 cpu 从 0.3 涨到 0.9（×3），同时 GPU `VideoDecode` 计数器整列消失、Dedicated 从 149.1 降到 57.4。这否掉了「关硬解降 GPU」这条路：它把占用从 GPU 挪到 CPU，反而更容易在低核数下丢帧。
3. **限核不额外省 CPU**。新掩码与不限核的 cpu 差在 0.0–0.2 个百分点，属噪声；限核真正改变的是**线程数**（101.4 → 90.4 / 102.0 → 91.4）和 **Private / Dedicated**（§5、§6.5）。所以「资源友好模式」的价值在内存与调度扰动，不在省 CPU。
4. **本次修复不降低占用数字，它纠正的是「用哪几个核」**。旧掩码 `0b1111` 在 16 核 32 线程的 Ryzen 上是物理核 0、1 加两个 SMT 兄弟 = 2 个物理核；新掩码 `0x55` 是物理核 0/1/2/3 = 4 个物理核。也就是说改动后给壁纸的算力翻倍，而对照表里的 cpu / GPU 数字没有恶化（1080p30 25.5→27.6 GPU 总、4K60 87.6→76.7 3D），换来的是 Private −24.6 %（406→306）与线程 −11。
5. **WMF 的代价体现在句柄和线程上**，不是 CPU：1080p30 句柄 2961 → 4022（+36 %），4K60 线程 91 → 114（+26 %）、句柄 → 4451（+50 %）。据此保持 FFmpeg 默认后端。
6. **高频暂停切换不累积**。345 次暂停 / 恢复后，线程从 93 降到 83、句柄从 2967 降到 2954、Private 末段均值 281.3 ≈ 首段 279.5，日志零错误；暂停段 cpu 掉到 0–0.04，说明定时器与解码线程确实停了。

2. **循环边界不再被怀疑**：`b_1080p24` 的 +107.5 drift 已改判为重绑伪影；soak30 前 445 s 内 44 次回绕未产生任何台阶跃。
3. **重绑有实测的一次性内存代价**（1080p30 上 +112 MB 显存 / +120 MB 提交），且该路径是既有代码、本任务未改；已确认可观测性缺口：`widgets=1/1` 不能证明窗口未重建（§9.2 与生命周期文档 §11.5）。
4. **4K60 提交内存的 490 s 三级台阶是新观测到的、未解释的现象**，也是本次唯一遗留的内存侧疑点，需要 ≥2 h 浸泡 + 用户态 GC/驱动侧计数才能定性。
