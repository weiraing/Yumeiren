# 视频壁纸内存归因实验报告（Phase 4 / 第二阶段任务书）

- 任务书：`VIDEO_WALLPAPER_MEMORY_INVESTIGATION.md`（内存归因与低风险优化验证）。
- 被测对象：`build/YumeirenTest.exe`（HEAD `ea2ad54`，含 `YUMEIREN_PROBE_STAGE` / `YUMEIREN_AUTO_STOP_MS` / `YUMEIREN_AUTO_START_MS` 环境变量探针钩子，正常运行不触发）；`build/SinkProbe.exe`（QVideoSink A/B 独立探针）。
- 环境：与 [perf-baseline.md](perf-baseline.md) 同机（Win11 26200 zh-CN，2560×1600@150%，32 逻辑核，RTX 5060 Laptop，Qt 6.10.2 MinGW，FFmpeg 后端 d3d11va 硬解）。
- 采样：`sample2.ps1` 每 5s 记录 Working Set / Private Bytes / CPU / 句柄 / 线程 / GPU 引擎利用率 / GPU 专用显存（Local Usage）/ GPU 共享显存（Shared Usage）；稳态统计剔除前 2 个采样点；原始 CSV 见 `results/inv_*.csv`，聚合脚本 `agg.py`。
- 素材：由用户原片（`build/media/video/凡人修仙传 紫灵.mp4`，H.264 3840×2160 60fps ~101Mbps 12.5s）用 libopenh264 派生统一编码参数的阶梯（`build/media/video/inv/`，CRF 无关、统一 8Mbps、High、yuv420p）。

## 指标口径（任务书第 4 节要求）

| 指标 | 含义 | 本报告用法 |
|---|---|---|
| Private Bytes | 进程私有已提交字节（`PrivateMemorySize64`） | 真实内存主指标；本进程共享提交可忽略，≈任务管理器"提交大小" |
| Commit Size | 提交虚拟内存总量（私有+共享提交） | 与 Private Bytes 差 <2%，不单列 |
| Working Set | 常驻物理内存，受 `SetProcessWorkingSetSize` 修剪 | 只作参考；**不得作为释放证据** |
| GPU Dedicated | `\GPU Process Memory\Local Usage` | 独立显存 |
| GPU Shared | `\GPU Process Memory\Shared Usage` | 共享显存（系统内存后备，**计入进程提交**） |

修剪实证：空闲阶段 WS 由 134MB 修剪到 3MB 时 Private 保持 67MB 不变——修剪≠释放（A/B/C 阶段均可复核）。

## 一、空播放器阶段归因（实验 3.1，1080p30，60s 稳态均值）

| 阶段 | Private | GPU 专用 | GPU 共享 | 线程 | 句柄 | CPU |
|---|---:|---:|---:|---:|---:|---:|
| A 空闲（无播放器） | 67 | 0 | 0 | 10–21 | ~1280 | 0 |
| B 创建 QMediaPlayer+QAudioOutput | 89 (+22) | 0 | 0 | 10–21 | ~1410 | 0 |
| C 设置媒体源 | 90 (+1) | 0 | 0 | 10–22 | ~1410 | 0 |
| D play()（无视频窗口） | 132 (+42) | 3.8 | 2.2 | 61 (+51) | ~2000 | 0 |
| E 挂载 QVideoWidget（不播放） | 138 (+48) | 26.3 | 22.2 | 44–56 | ~2280 | 0 |
| F 完整播放 | 403 (365–448) | 231 | 191 | ~105 | ~3045 | 0.2 |

结论：`创建播放器 +22MB`（加载 Qt FFmpeg 后端 DLL 与集成层）、`设置源 +1MB`、`播放机制 +42MB`（线程池为主，**无视频输出时视频解码不真正启动**，GPU 仅 3.8MB）、`呈现表面 +48MB 私有 + 48MB GPU`（交换链）；**真正的大头在 F−E：+265MB 私有、+205MB 专用显存、+169MB 共享显存 = 解码器帧池 + D3D11VA 解码表面 + 呈现队列**。1080p 时 GPU 专用+共享 ≈ 422MB，与 Private ≈ 403MB 高度吻合（共享显存以系统内存后备计入进程提交）。

## 二、分辨率/帧率对照（实验 3.2，统一 libopenh264 8Mbps，180s 稳态）

| 素材 | Private | GPU 专用 | GPU 共享 | GPU% |
|---|---:|---:|---:|---:|
| 720p30 | 289 | 130 | 82 | 16.8 |
| 1080p30 | 404 | 236 | 205 | 25.8 |
| 1440p30 | 595 | 419 | 382 | 29.5 |
| 4K30 | 944 | 722 | 659 | 72.8 |
| 4K60 | 928 | 703 | 658 | 90.5 |
| 1080p60 | 401 | 233 | 187 | 48.9 |

- 内存与**分辨率（像素数）近似线性**：拟合 ≈ 固定 ~210MB + ~88MB/百万像素（≈ 约几十个解码表面/帧池随分辨率放大）。
- **帧率对内存无影响**（4K30≈4K60、1080p30≈1080p60），帧率只影响 GPU 利用率（16.8%→90.5%）。帧池按缓冲个数而非秒数分配。
- 全部场景 3 分钟稳态无单调增长。用户原片（101Mbps 同内容）包络 957–1257MB，比 8Mbps 重编码（806–1122）高 ~15%——编码码率/参数也影响池规模。

## 三、编码格式对照（实验 3.3，1080p30，180s 稳态）

| 编码 | 解码方式 | Private | GPU 专用/共享 | GPU% | CPU |
|---|---|---:|---:|---:|---:|
| H.264 | d3d11va 硬解 | 404 | 236 / 205 | 25.8 | 0.2% |
| HEVC（hevc_d3d12va 编码） | d3d11va 硬解 | 369 | 216 / 157 | 31.2 | 0.2% |
| AV1（SVT-AV1 编码） | 硬解 | 267 | 182 / 148 | 31.4 | 0.2% |
| VP9 | 未测：本地 ffmpeg 8.1.2（conda 版）无 VP9 编码器（libx264/libx265/libvpx-vp9 均缺，hevc_mf 不可用后改用 hevc_d3d12va） | — | — | — | — |

- 无任何格式触发软件解码或硬解回退（CPU 均 0.2%）。
- AV1 路径内存最省（比 H.264 少 ~34%），HEVC 略省（~9%）。

## 四、音频对照（实验 3.4，1080p30 含 AAC 音轨，125s 稳态）

| 场景 | Private | GPU 专用/共享 | CPU |
|---|---:|---:|---:|
| 音量 0（应用按策略禁用音频轨） | 399 | 236 / 152 | 0.2% |
| 音量 100（音频轨激活） | 398 | 231 / 156 | 0.2% |
| 无音频轨（同素材 3.2 基线） | 404 | 236 / 205 | 0.2% |

结论：**音频对内存无可测影响（≤5MB 噪声）**。既有"音量 0 禁用音频轨"优化的收益在音频解码线程/设备占用，不在内存。

## 五、关闭与重载（实验 3.5，受控显示器保活）

| 阶段 | Private | GPU 专用/共享 | 线程 | 句柄 |
|---|---:|---:|---:|---:|
| 播放（90s） | 397 | 231 / 190 | ~105 | ~3046 |
| `stopAll()` 后 30s | **95** | **0 / 0** | 18 | 1458 |
| 重载同视频后 | **395** | 232 / 167 | ~94 | ~3014 |

- 关闭后 Private 回落到 ~95MB（≈B 阶段 89MB + 图库/设置残差），**GPU 内存归零**，`deleteLater()` 确认已执行（句柄/线程回落）。
- 重载回到相同基线（395 vs 397），**无逐次累积**。
- 意外收获：第一批重载实验中系统空闲触发显示器关闭，实际走通「熄屏暂停 → 180s 长挂起自动释放管线（Private 365→93MB、GPU→0）→ 恢复播放重建（275MB，低于首次）」全链路——挂起释放机制在真实事件下验证通过且无残留。

## 六、QVideoSink A/B 实验（SinkProbe，仅保留最新帧 + 每帧 toImage 绘制）

| 场景 | QVideoWidget（生产路径） | QVideoSink 探针 | 结论 |
|---|---:|---:|---|
| 1080p30 Private | 403 (365–448) | **517 (449–617)** | +28%，且波动大（每帧 QImage 分配抖动） |
| 1080p30 CPU | 0.2% | **1.4%** | ×5.5 |
| 1080p30 GPU 专用/共享 | 236 / 205 | 212 / 152 | 后端池仍在，未减少 |
| 4K60 Private | 928 | **1111** | +20% |
| 4K60 CPU | 0.4% | **2.2%** | ×5.5 |

**按任务书规则（"不能显著降低内存立即停止"）：QVideoSink 方向停止，不扩大重构。** 内存持有者是 FFmpeg 后端解码池/D3D11VA 表面，QVideoSink 路径既消不掉它们，还额外引入 CPU 侧帧缓冲与每帧 `toImage()` 转换。

## 七、低风险代码检查结论（任务书第 5 节）

- 5.1 播放器生命周期：QMediaPlayer/QVideoWidget/QAudioOutput 均单实例复用（`videowallpaper.cpp:261-273` 仅在 `m_outputs` 为空时经 `makeOutput` 创建）；信号只在创建时连接一次；teardown 统一 `deleteLater`（`:243-259`），父对象为静态单例，无双重释放。
- 5.2 视频输出生命周期：`ensureOutputs` 非空仅轻量重挂载；多屏模式值不变不重建（`:417-419`）；错误重试走 `playIndex`→`ensureOutputs` 不新建播放器；`m_outputs` 清空即时。
- 5.3 挂起状态：暂停即停解码（CPU/GPU→0，本批与 S6'' 实证）；锁屏/熄屏/遮挡暂停 + 180s 长挂起整管释放（本批重载实验在真实熄屏事件下走通）；恢复经 LoadedMedia 跳回原进度，重建不叠加资源。
- **未发现需要 P0/P1 修复的实际问题；本阶段除探针/工具外未修改任何生产逻辑。**
