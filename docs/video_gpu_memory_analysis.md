# 视频壁纸 GPU 与显存分析（Yumeiren）

数据来源：`new-build/perf-results/b_*.csv`（改动前）、`v_*.csv`（改动后与开关对照），汇总在 `summary_baseline.csv` / `summary_verify.csv`。采集器与口径见 `video_performance_baseline.md` §2。

## 1. 谁在做 GPU 工作

本机只有**一块 GPU 在驱动桌面**：AMD Radeon 610M（性能计数器实例前缀 `p0_`）。NVIDIA RTX 5060 Laptop 在位但无输出分辨率（混合显卡模式下独显不驱动屏幕），`nvidia` 系列计数器对本进程全为空。**因此本文所有 GPU 数字都是 610M 的**，与仓库 HEAD 里那份历史基线（曾记录 RTX 5060）不是同一张卡路径，绝对值不可跨文档比较。

呈现链路（代码 + 计数器共同支撑）：

```text
文件 → QMediaPlayer(FFmpeg 后端) → d3d11va 硬解(GPU Video Decode 引擎)
     → NV12 纹理留在显存 → QVideoWidget 的 QRhi/D3D11 呈现器(3D 引擎做 NV12→RGB + 缩放)
     → 交换链呈现到 WorkerW 下的子窗口 → DWM 合成到屏幕(2560×1600@165Hz)
```

应用层没有第二份绘制代码（无逐帧 `QImage`/`QPixmap`、无 `QPainter`、无 layered/透明窗口），grep 证据见 `video_performance_audit.md` §5.3。

## 2. GPU 解码路径（Video Decode 引擎）

| 用例 | 素材 | VideoDecode % | 说明 |
|---|---|---|---|
| `b_idle` | 无 | 无该计数器实例 | 空闲时解码引擎不参与 |
| `b_1080p30` | H.264 1080p30 | 10.1 | 硬解生效 |
| `b_1080p60` | H.264 1080p60 | 19.9 | 帧数翻倍，成本 1.97 倍 |
| `b_2160p60` | H.264 4K60 | 61.4 | 与 1080p60 比 3.1 倍（像素 4 倍） |
| `b_av1_4k60` | AV1 4K60 | 44.9 | **同分辨率 AV1 比 H.264 省 27% 解码引擎** |
| `v_swdecode_1080p30` | H.264 1080p30 强制软解 | **该计数器消失** | 决定性证据：默认走硬解 |

强制软解的方法：`QT_FFMPEG_DECODING_HW_DEVICE_TYPES=vaapi`（AMD 上没有 vaapi，等于把硬件设备类型清空 → 回退 CPU 解码）。这一档的完整代价：

| 指标 | 硬解（默认） | 强制软解 | 变化 |
|---|---|---|---|
| CPU %（32 核归一） | 0.20 | 0.90 | **×4.5** |
| GPU 引擎合计 % | 25.5 | 12.5 | -51% |
| 3D % | 15.4 | 12.5 | -19% |
| Private (MB) | 313.9 | 217.5 | -31% |
| Dedicated (MB) | 149.1 | 57.4 | -62% |
| Shared (MB) | 108.9 | 46.2 | -58% |
| 线程 | 91 | 58 | -36% |
| 句柄 | 2972 | 2328 | -22% |

**这张表看起来很诱人，但任务书明确禁止用「关硬解」换 GPU 数字，本次也没有这么做**（默认仍是硬解）。理由三条：
1. 0.9% 是 32 逻辑核归一后的值，约等于 29% 单核；1080p30 尚且如此，4K60 的像素×帧率是 16 倍，软件解码会吃掉数个物理核，笔记本上直接反映为发热与掉电。
2. 内存下降的本质是「显存帧池换成系统内存帧池 + 解码线程减少」，而线程减少是因为 FFmpeg 不再按核数开多线程解码器。这些收益与「把进程限制到 4 核」是同一笔钱，不能叠加。
3. 关硬解后 GPU 与 DWM 的功耗状态会变差（解码引擎空闲不等于整机省电），本机现有工具无法量化 → 未验证。

## 3. 3D 引擎路径（NV12→RGB 色彩转换 + 缩放 + 提交呈现）

这是本模块 GPU 占用的**大头**，也是唯一随帧率线性变化的部分。基线帧率阶梯（同一素材源派生、`TargetFps=0` 交回原始帧率、90s）：

| 用例 | 呈现帧率 | 3D % | VideoDecode % | 3D 单位帧成本（%/帧） |
|---|---|---|---|---|
| `b_1080p15` | 15 | 7.1 | 5.3 | 0.47 |
| `b_1080p24` | 24 | 12.8 | 8.2 | 0.53 |
| `b_1080p30` | 30 | 15.4 | 10.1 | 0.51 |
| `b_1080p60` | 60 | 31.2 | 19.9 | 0.52 |
| `b_60dup` | 60（其中一半是重复帧） | 31.6 | 20.1 | 0.53 |
| `b_still30` | 30（画面完全静止） | 13.7 | 12.8 | 0.46 |

四条结论，全部由上表直接读出：

1. **3D 成本与「呈现了多少帧」线性相关**，1080p 下约 0.5 %/帧，15→60 帧的斜率几乎没有亚线性或超线性。
2. `b_60dup ≈ b_1080p60`（31.6 vs 31.2）→ **重复帧照样付全价**，呈现链路不做去重，所以「靠降帧率省 3D」必须是真少提交帧，而不是内容不变。
3. `b_still30 ≈ b_1080p30`（13.7 vs 15.4，差异在采样抖动内）→ 成本**与画面内容复杂度无关**，是每帧固定的色彩转换 + 缩放 + 提交开销。
4. 因此**排除「165Hz 面板按刷新率结算」**这一怀疑：若按 165Hz 结算，15fps 档的 3D 应该是 60fps 档的 1/4，且静止画面不可能与运动画面同价。面板刷新由 DWM 承担，不进入本进程的 3D 计数器。

单位帧成本随**源分辨率**增长，而不是随目标窗口大小：

| 用例 | 源 | 帧率 | 3D % | %/帧 |
|---|---|---|---|---|
| `b_1080p30` | 1920×1080 | 30 | 15.4 | 0.51 |
| `b_2160p30` | 3840×2160 | 30 | 57.5 | 1.92 |

比值 3.76，接近像素比 4.0。也就是说 4K 素材在呈现阶段**先按 4K 做完色彩转换与缩放，再丢掉约一半像素**。Qt Multimedia 的 `QVideoWidget` 呈现器没有暴露「上传前缩放 / 在解码器里缩放」的公开 API，唯一能做的是自绘 video sink，而这条路在本仓库历史 A/B 里已被否决（内存 +28%、CPU ×5.5）。**本次不改呈现方式。**


## 4. Copy 引擎

| 用例 | Copy % | 说明 |
|---|---|---|
| FFmpeg 后端全部用例（`b_*`、`v_newmask_*`、`v_nolimit_*`、`v_swdecode_*`） | **计数器实例不存在** | 采样时本机 GPU Engine 列表里没有该进程的 `p0_copy` 实例，故原始 CSV 连列都没有 |
| `v_wmf_1080p30` | 3.28（稳定） | WMF 后端全程使用 Copy 引擎 |
| `v_wmf_4k60` | 11.46 / 11.28 / 11.20 / 11.53（前 40 s），46 s 后降到 0 并出现空实例 | **勘误**：前 40 s 与后 70 s 不是同一状态，12:30:04.523 的窗口重绑把会话切成两段；「稳态 11.3%」不成立，只能说明 WMF 在 4K 下确实使用 Copy 引擎，需重测 |

读数：FFmpeg + d3d11va 路径**不额外占用 Copy 引擎**（上传与格式转换由 Decode/3D 引擎自己承担），WMF 路径多一条 GPU 内拷贝。这是「不切换后端」的又一条量化理由，见 §6。

## 5. Dedicated（本地显存）与 Shared（共享系统内存）

`GPU Local Memory Usage`（本表记为 Dedicated）与 `GPU Shared Memory Usage`（记为 Shared），单位 MB。

| 用例 | 源 | Dedicated | Shared |
|---|---|---|---|
| `b_1080p15` | H.264 1080p15 | 149.1 | 121.0 |
| `b_1080p24` | H.264 1080p24 | 190.2 (勘误，见 §3) | 150.3 (勘误) |
| `b_1080p30` | H.264 1080p30 | 149.1 | 108.9 |
| `b_1080p60` | H.264 1080p60 | 149.0 | 108.0 |
| `b_60dup` | 1080p30 重复呈现 | 149.0 | 100.0 |
| `b_still30` | 1080p30 静止 | 149.1 | 102.2 |
| `b_2160p30` | H.264 4K30 | 434.0 | 414.6 |
| `b_2160p60` | H.264 4K60 | 433.8 | 410.6 |
| `b_raw_4k60` | MPEG-4 4K60 | 555.2 | 523.2 |
| `b_av1_4k60` | AV1 4K60 | 910.0 | 871.0 |

读出的规律：

1. **显存池随源像素走，与帧率无关**：4K30 = 434.0 与 4K60 = 433.8 一致；1080p30 = 149.1 与 1080p60 = 149.0 一致。因此降 fps 不会省显存，降源分辨率才会。
2. **编码格式影响池大小**：同为 4K60，AV1 是 H.264 的 2.1 倍（910 vs 434），MPEG-4 居中（555）。AV1 需要更多参考帧与格式缓冲，但解码引擎反而省 27%（§2），两者不能互相抵消地看待。
3. **勘误（2026-09-15 复核）**：`b_1080p24` 的 190.2 不是码流特性，而是窗口重绑污染出来的平均值。该会话 11:58:58 启动，日志在 **12:00:03.484**（elapsed ≈ 65 s）记录一次壁纸窗口失效重绑；同一份 CSV 里 Dedicated 从 elapsed 12.1–60.9 的 **149.1** 阶跳到 68.8–92.5 的 **241.5**，Shared 同步从 104 升到 188–204。聚合脚本丢弃前 2 点后取整段均值，等于把跳变前 5 点与跳变后 4 点平均 → 190.17 ≈ 190.2，这个数在任何时刻都没有真实存在过。`r_switch` 重放同一份 24fps 素材、会话内无重绑事件（12:46:08.901 起），29 个 Dedicated 样本全部落在 **136.5–149.6（均值 140.8）**，从未复现 190.2，此前「精确复现」的说法不成立。修正后的规律：**1080p 各档（含 24fps）稳态池同为 149 一档，不存在码流特例**；真正会换池的是重绑（149.1 → 241.5）。
4. Shared 与 Dedicated 基本同比例变化（Dedicated 的 0.7~0.96 倍），说明帧池同时持有显存纹理与一份系统内存映射，不是显存不足溢出到共享内存。

## 6. 后端对照与核数上限对 GPU 资源的影响

同一素材、同一口径（TargetFps=0，新构建）下换后端：

| 指标 | FFmpeg（默认） | WMF | 差异 |
|---|---|---|---|
| 1080p30 Private (MB) | 305.8 | 347.4 | WMF +13.6% |
| 1080p30 句柄 | 2961 | 4023 | WMF +36% |
| 1080p30 线程 | 90.4 | 89.9 | 持平 |
| 1080p30 GPU 合计 % | 27.6 | 30.9 | WMF +3.3 |
| 1080p30 Copy % | 无实例 | 3.28 | WMF 多一条拷贝路径 |
| 4K60 Private (MB) | 667.4 | 575.6 † | **不可用** |
| 4K60 线程 | 91.4 | 114.2 † | **不可用** |
| 4K60 句柄 | 2971 | 4452 † | **不可用** |
| 4K60 3D % | 76.7 | 57.6 † | **不可用** |
| 4K60 VideoDecode % | 64.8 | 61.4 † | **不可用** |

† **勘误（2026-09-15 复核）**：WMF 4K60 会话起于 12:29:24，日志在 **12:30:04.523**（elapsed ≈ 40 s）记录了一次壁纸窗口重绑，CSV 在 38.2→46.2 s 之间发生阶跃：`p0_copy` 11.2～11.5 归零、`p0_loc` 567.5→438/456.1、线程 92→123、句柄 4030→4580。整段均值把重绑前后混在一起，因此**上表 4K60 各行（含「线程 +25%」「句柄 +50%」「3D -19.1」与「Copy 稳态 11.3%」）一律不可用于后端结论**，需重测。1080p 各行不受影响。

结论：**1080p 下 FFmpeg 全面更省**（Private -13.6%、句柄 -36%、无 Copy 拷贝路径），该项有干净的对照数据支持。4K60 的 WMF 对照因上述污染作废，不下结论。任务书要求保持既有播放链路，且换后端属于「重写播放器」级别的风险，故**不切换**，保持 FFmpeg 默认。

核数上限对显存的影响（同构建，只改 `AffinityLimit`）：

| 指标 | 不限核 | 限 4 物理核 | 变化 |
|---|---|---|---|
| 1080p30 Dedicated (MB) | 237.4 | 149.1 | **-37.2%** |
| 1080p30 Shared (MB) | 181.3 | 122.7 | -32.3% |
| 1080p30 Private (MB) | 406.0 | 305.8 | -24.7% |
| 1080p30 线程 | 101.4 | 90.4 | -10.8% |
| 4K60 Dedicated (MB) | 693.0 | 406.0 | **-41.4%** |
| 4K60 Shared (MB) | 669.5 | 383.9 | -42.7% |
| 4K60 Private (MB) | 976.8 | 667.4 | -31.7% |
| 4K60 线程 | 102.0 | 91.4 | -10.4% |
| 1080p30 GPU 合计 / 3D / Video % | 25.7 / 15.7 / 10.1 | 27.6 / 17.5 / 10.0 | 基本持平 |
| 4K60 GPU 合计 / 3D / Video % | 138.7 / 77.4 / 61.3 | 141.5 / 76.7 / 64.8 | 基本持平 |

机制解释（推断，非直接测量）：FFmpeg 多线程解码器按可用核数决定线程与帧池深度，核少了 → 线程 -10%、参考帧/输出队列变浅 → 显存帧池与配套的提交内存同时下降。**限核换来的是内存与显存，不是 GPU 占用**：GPU 三项在限核前后持平，4K60 的 3D 甚至仍停在饱和区。

## 7. 分级结论

### 已确认（有本机数字）

1. 默认走**硬解 d3d11va**：VideoDecode 引擎全程有占用；强制清空硬件设备类型后该计数器实例消失、CPU 从 0.20 升到 0.90。
2. 3D 引擎是**第一大 GPU 开销**，成本与「呈现帧数 × 源像素」线性相关：1080p 每帧 0.46~0.53%，4K 每帧 1.92%（比值 3.76 ≈ 像素比 4.0）。
3. 4K60 下三种不同编码素材的 3D 全部落在 87.6~88.3%，线性外推需 ~116% → **4K60 呈现已达 3D 引擎上限**。
4. 显存池只随源分辨率变化（4K30 434.0 vs 4K60 433.8），AV1 4K60 需要 910 MB，是 H.264 的 2.1 倍。
5. FFmpeg 后端不使用 GPU Copy 引擎，WMF 使用（1080p30 实测 3.23–3.32%，会话内平稳）。4K60 的 WMF 对照已不可用：其 Copy 只在重绑前的 4 个样本为 11.20–11.53%，重绑（12:30:04.523）后直接归零，见 §6。
6. 限制到 4 个**不同物理核**后：Dedicated 显存 -37%（1080p30）/ -41%（4K60），提交内存 -25% / -32%，线程 -10%，GPU 占用不变。

### 可能（证据间接）

1. 4K60 的 3D 饱和很可能表现为**丢帧而非卡顿可见**（壁纸窗口不是前台窗口，DWM 会以可丢帧方式合成）→ 需要帧间隔数据才能定性。
2. `b_1080p24` 的 +107.5 MB `private_drift` 已由「循环边界瞬时叠加」改判为**窗口重绑污染**：该用例 Private 轨迹是 315.1（重绑前最后一个样本）→ 378.3 → 421.2 → 421.5 → 425.4，一次性阶跃后停在 421~425 高位，与 Dedicated 149.1→241.5 同步，不是循环周期的往复锯齿。同口径对照组 `b_1080p30`（同一素材家族、10 s 循环约 9 次、会话内无重绑）min 276.7 / max 348.6、drift 只有 +4.1，没有出现这种单台阶跃。40 分钟浸泡（r_soak30_1080p30）独立复现同一机制：以重绑为界，Private 由 274.9~357.0（均值 305.2，22 点）换到 389.8~467.5（均值 425.2，102 点），Dedicated 由均值 150.5 换到 262.5；第二次重绑未再抬层，说明是一次性换池而非泄漏。生命周期侧取证见 `video_resource_lifecycle.md` §4、§11.5。
3. 610M 是 iGPU，Shared 部分直接占用系统内存带宽，所以「显存」在这台机器上不是独立资源，降显存与降 Private 是同一件事的两面。

### 已排除（不是 GPU 占用来源）

- 逐帧 `QVideoFrame::toImage()` / `QImage::fromImage` / 每帧转 `QPixmap`：代码中不存在（grep 见 `video_performance_audit.md` §5.3）。
- 应用侧 `QPainter` 自绘视频、layered 窗口、`setWindowOpacity`、透明背景：均不存在。
- 按 165 Hz 面板刷新率结算呈现：被 fps 阶梯实验否定（15 fps 只有 7.1%，若按刷新结算应与 60 fps 同价）。
- 画面内容复杂度（静止 vs 运动）：无差异。
- 音量/音频轨道：静音时已 `setActiveAudioTrack(-1)`，不产生 GPU 开销。
- 1 s 心跳定时器与 30 s 内存裁剪：只触发 `SetProcessWorkingSetSize(-1)`，且裁剪只在无输出/手动暂停/挂起时执行，不驱动 GPU。

### 未确认（本机现有工具做不到）

1. **实际呈现帧率与丢帧位置**：需要 PresentMon / ETW Present 事件，本机未安装。
2. **每帧在 Decode 与 3D 引擎上的分解耗时**：计数器只给引擎级利用率，不给 per-frame。
3. **D3D11 资源级显存明细**（哪个纹理、多少 mip）：需要 PIX / D3D Debug Layer，且 Debug Layer 本身会改变性能。
4. **RTX 5060 独显路径**：本机构型下独显无输出分辨率，壁纸不可能跑在独显上。
5. **多屏 MonitorOnly / MirrorAll 下的 GPU 成本**：本机单屏，无法验证；只能按「每输出一个窗口、呈现帧数相加」推断为线性。
